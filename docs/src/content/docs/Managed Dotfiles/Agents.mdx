## Claude Code

`~/.claude/settings.json` is tracked as a plain file.

- `CLAUDE_CODE_SHELL` pins the Bash tool to Homebrew bash.
- `skipDangerousModePermissionPrompt` is on; the shell alias adds `--dangerously-skip-permissions`.
- Plugins: ponytail, i-have-adhd, frontend-design.
- `~/.claude/skills/nano-banana` generates images through the Gemini CLI, which mise installs. It needs `GEMINI_API_KEY` in `~/.config/secrets.env`.

`~/.claude/CLAUDE.md` holds one line, `@~/.codex/AGENTS.md`, so Claude Code reads the same global instructions as Codex.

Memory, history, and project state under `~/.claude` are not tracked.

## Skills

Shared skills live in [`kiliantyler/skills`](https://github.com/kiliantyler/skills), checked out at `~/git/kiliantyler/skills`. `run_onchange_after_link-skills` clones that repo if it is missing, links each `skills/<name>/` into `~/.claude/skills`, `~/.codex/skills` and `~/.agents/skills`, and unlinks repo skills that were deleted. It never pulls the repo, and it leaves alone any entry that is not a link into it (third-party installs, plugin links), printing a note when one shadows a repo skill of the same name. It re-runs when `gh` sign-in, the checkout's presence, or the repo's list of skills changes, so a new or deleted skill is linked or unlinked on the next apply and `chezmoi status` stays empty otherwise.

## Codex

`~/.codex/AGENTS.md` is tracked: the global agent instructions both Codex and Claude Code load in every session. They send every home-directory change through the `dotfiles` skill in `kiliantyler/skills`, which walks the chezmoi workflow in this repo. Edit it in place, then run `chezmoi re-add ~/.codex/AGENTS.md`. Nothing else under `~/.codex` is tracked. Codex reads the login shell from the user record and its own secrets from `~/.codex/secrets/`, which `~/.bashrc` also sources so both agents share variables.

## macOS build isolation

`~/.local/bin/macos-build` runs a command from the current Git working copy in a disposable Tart clone of the prepared `t3-macos-build` image. Each admitted job owns a slot and gets four virtual CPUs and 8 GiB RAM. The runner clones the stopped base with APFS copy-on-write, boots only that job's clone without host directories or clipboard sharing, transfers a Git bundle and the actual tracked and untracked source bytes, and runs the command at the matching subdirectory. It stops and deletes its clone after success or failure. The prepared base stays unchanged, so each job's disk changes can be discarded. Git-ignored files and host credentials are not copied. Submodule working copies are rejected rather than validated without their contents. Install dependencies inside the guest using the repository's existing setup commands.

Admission allows up to two concurrent jobs. It budgets four host CPUs, 12 GiB host RAM, and another 2 GiB per guest for VM overhead. Smaller hosts get fewer slots or a refusal. New jobs require normal host memory pressure; admitted jobs keep their slot until cleanup completes. A waiting admission owner retains its place so new arrivals cannot bypass it, then releases the admission lock before building. Running jobs own independent slot leases. The old global lease remains a shared compatibility lock: an older runner or prepared-image maintenance takes it exclusively, so upgrades drain existing owners without interrupting them.

```sh
macos-build -- swift test --jobs 4
macos-build --wait -- swift test --jobs 4
macos-build --artifact .build/test.log -- /bin/bash -o pipefail -c 'mkdir -p .build; swift test --jobs 4 2>&1 | tee .build/test.log'
macos-build --postgres -- /bin/bash -c 'pnpm install --frozen-lockfile && pnpm check'
```

`--postgres` creates a fresh PostgreSQL 18 cluster for that job, waits for it to start, and sets `TEST_DATABASE_URL` for the command. It listens only on guest loopback, uses the job's private directory for data and logs, and is discarded with the owned VM. Prepare the base image with `brew install postgresql@18` inside the guest; the host needs no PostgreSQL service. Install the repository's pinned Node and package-manager versions inside the guest too. This option supplies a database for test suites that support `TEST_DATABASE_URL`; Docker-specific tests still require a Docker-capable runner.

Artifact paths are relative to the repository root and must be Git-ignored. They are the only build outputs copied back to the host. A missing or already-running base, full slots, memory pressure, or insufficient host disk space fails the request. `--wait` waits for a slot and normal memory pressure; cancelling a waiter leaves active owners alone. Each `~/.local/state/macos-build/slot-*/lease` records its host PID and repository, with that slot's runtime log and deferred cleanup record beside it. The runner checks a 20 GiB host reserve before starting, during execution and during artifact export, and stops only its own clone if the reserve is crossed. Failed deletion retains the exact job VM for later cleanup; a still-running deferred VM requires owner inspection and is never taken over. Cleanup errors do not replace the original failure. Job clones are excluded from Time Machine backup copies. The runner never runs the command locally as a fallback. Its disposable guest checkout preserves the source HEAD and pending edits. Repository commits, pushes, tracker writes and release signing stay on the host.

The VM image, guest disk, lease and runtime log are application state. They stay outside chezmoi. The runner and its command policy are managed files. Run its fixture tests with `python3 -m unittest discover -s tests -p 'test_macos_build.py'` from the dotfiles repository.

## VS Code

`~/Library/Application Support/Code/User/settings.json` is tracked. VS Code rewrites it when settings change in the UI, so after a change run:

```sh
chezmoi re-add "$HOME/Library/Application Support/Code/User/settings.json"
```

Extensions are not tracked.
